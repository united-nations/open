# AGENTS.md

This file provides guidance to AI coding agents when working with code in this repository.

## Project

The **UN Transparency Portal** is a static Next.js app that visualizes financial data across the UN System and the UN Secretariat: contributions, entity spending, geographic deployment, SDG funding, Secretariat budgets, field missions, and trust funds. The frontend reads pre-processed static JSON; a separate Python pipeline produces that JSON from raw sources.

The portal currently previews at [open.unfck.org](https://open.unfck.org) but the production destination is **[open.un.org](https://open.un.org)** (the official UN transparency gateway).

## Commands

```bash
npm run dev          # Next.js dev server (localhost:3000)
npm run build        # Static export to out/ (output: 'export')
npm run typecheck    # tsc --noEmit (strict mode)
npm run lint         # eslint
npm run format       # prettier --write on src/

uv run python/NN-<script>.py   # Run a data pipeline step
```

Package manager is **pnpm** (`pnpm-lock.yaml`, used in CI), though `npm run` works locally. Python uses **uv** (`uv.lock`, Python 3.13+). There is no test suite.

## Architecture

### Two-stage data flow

1. **Python pipeline** (`python/`) — numbered scripts run **in order** (`01-` … `10-`, then `99-`). They fetch from Airtable, CEB Financial Statistics, member-state scrapes, and the UNINFO API, fuse the sources (CEB + Secretariat breakdowns), and export to `public/data/`. Raw/intermediate data lives in `data/` (gitignored), keyed by stage: `data/ceb/{raw,clean,fused}/`, `data/uninfo/raw/`. `python/utils.py` holds canonical name normalization maps (`ENTITY_MAPPING`, `DONOR_MAPPING`) — reuse these rather than reinventing name matching.
2. **Frontend** reads `public/data/` at runtime via `fetch`. Data is served as static files, never via API routes (the app is a static export).

### Data file conventions (`public/data/`)

- `{view}-{year}.json` — one file per visualization per year (e.g. `donors-2024.json`, `entity-spending-2023.json`).
- `manifest.json` — generated by `python/99-generate_manifest.py`; declares available years and the default year per dataset. The frontend reads this to drive year sliders. Regenerate it after adding/removing year files.
- `uninfo-countries/` — 127 per-country files.

Loading goes through helpers in [src/lib/data.ts](src/lib/data.ts): `loadYearData(dataset, year)` and `loadStaticData(filename)`. All fetches are prefixed with `NEXT_PUBLIC_BASE_PATH` for GitHub Pages compatibility.

### Domain data model (read `docs/` before touching the pipeline)

The portal combines **three non-equivalent financial datasets** — they use different methodologies, scopes, and granularity, and must not be naively summed:

- **CEB Financial Statistics** (2011–2024, ~43–48 entities) — system-wide actuals from audited statements. The reconciled backbone for contributors, entity revenue/spending, countries, and SDG views. Annual-cycle, lagged. Critically, CEB does **not** net out inter-agency transfers, so totals are inflated by double-counting.
- **UN Secretariat** (2019–2023, ~150 sub-entities) — granular breakdown of the CEB `UN` and `UN-DPO` aggregates into individual departments, offices, and peacekeeping/political missions (OCHA, DPPA, DSS, MONUSCO, etc.). Used to enrich CEB expenses in fusion years; consolidated accounting that _does_ eliminate inter-entity transfers, so its totals run slightly lower than CEB.
- **UNINFO** (2022–2024, 127 programme countries) — Cooperation Framework data with per-project detail and the **SDG×country** cross-dimension the other two lack. Tracks three metrics that always satisfy Required ≥ Available ≥ Spent. Covers only ~40–45% of system spending (no HQ, peacekeeping, or donor countries). Powers per-country sidebars/projects/results-framework.

Key fusion logic (see [docs/data-fusion-revenue.md](docs/data-fusion-revenue.md), [docs/data-fusion-expenses.md](docs/data-fusion-expenses.md)):

- **Revenue fusion is tiered** (CEB only): 2013–2020 = government + non-gov donors + a single "Other" remainder; 2021–2024 = "Other" broken into contributor-type categories (C-codes C01–C09). Named donors vs. calculated remainders are flagged via `is_other`.
- **Expenses fusion is tiered** (CEB + Secretariat): 2019–2023 removes the CEB `UN`/`UN-DPO` aggregates and substitutes the ~150 Secretariat sub-entities (plus additive assessed amounts for UNEP/UNODC); other years use CEB as-is. This is why entity counts jump from ~40 to ~180 in fusion years. The `source` column tags each row as `ceb`, `secretariat`, or `secretariat_assessed`.
- **CEB `UN` vs `UN-DPO`**: `UN` = Secretariat incl. Special Political Missions; `UN-DPO` = peacekeeping operations (aggregate only, no per-mission breakdown — the per-mission detail comes from the Secretariat dataset). UNEP/UNODC/UN-Habitat/ITC have separate CEB entries despite being administratively Secretariat.
- **Data-quality gotchas** handled in `python/utils.py`: negative amounts are legitimate (FX losses, corrections); C08B is an unreliable correction bucket; donor name/category variants are normalized via `DONOR_MAPPING`/`DONOR_CATEGORY_OVERRIDES`; generic catch-all donors marked via `GENERIC_DONORS`.

### Frontend structure

- `/` is a directory (no charts): two boxes linking to System and Secretariat sub-pages, plus Further Resources.
- `/system` and `/secretariat` share the same chrome (`SectionChrome`: title, intro, tab row). Each tab is its own route. `/system/` re-exports `/system/contributors`.
- System tabs: Contributors, Organizations, Locations, Goals. Secretariat tabs: Overview, Contributors, Programme Budget, Peacekeeping Budget, Field Missions, Trust Funds.
- Per-view components follow naming families that sort together: `*Treemap`, `*Sidebar`, `*TrendsChart`. Reusable chart primitives in `src/components/charts/`; shadcn primitives in `src/components/ui/` (do not edit these — compose on top of them). Shared page chrome: `SectionChrome`, `SectionSubnav`, `PageHeading`, `Methodology`.
- `src/lib/` holds domain mappings consumed by components: `entities.ts`, `contributors.ts`, `sdgs.ts`, `financingInstruments.ts`, `regionGroupings.ts`, `systemGroupings.ts`, `navigation.ts`. Shared TS interfaces in `src/types/index.ts`.

### Deep linking (hash-based)

Sidebar navigation is driven by the URL hash on the matching route (`/system/contributors/#donor=…`, `/system/organizations/#entity=…`, `/system/locations/#country=…`, `/system/goals/#sdg=…`), not by in-page section jumps across tabs. Use the helpers in [src/hooks/useDeepLink.ts](src/hooks/useDeepLink.ts): `navigateToSidebar` (pushes history), `replaceToSidebar` (no history entry), `clearSidebarHash`. The `useDeepLink` hook parses the hash, scrolls to the section, and listens for `hashchange`/`popstate`.

## Deployment

GitHub Actions (`.github/workflows/nextjs.yml`) builds the static export and deploys to GitHub Pages on push to `main`. `basePath` is managed manually in [next.config.ts](next.config.ts) (the Next static-site action was removed); it is empty for the custom domain and falls back to `BASE_PATH` env var. Use `NEXT_PUBLIC_BASE_PATH` for any asset/data URL in code.

## Conventions (from .github/copilot-instructions.md)

- Server Components by default; add `"use client"` only for interactive pieces.
- PascalCase for component filenames; kebab/snake_case for other files. Name similar components so they sort together.
- Strict TypeScript, no `any`. Add shadcn components via `npx shadcn@latest add <component>`.
- Design: left-align, minimal, clear hierarchy, UN color palette (especially `un-blue`).
- Avoid parallel infrastructure — prefer the existing global mappings in `src/lib/` and `python/utils.py`.
